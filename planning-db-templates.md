# Load report HTML from the database (student-gradesheet; id-card stays file-based)

## Context

Right now `POST /api/v1.0/print` with a `report` field only works with files. The report HTML comes from `classpath:/reports/`, and its CSS, SVGs and fonts come from `classpath:/templates/<template>/`. The goal is to **move only the report HTML into a database**, using the same retrieval method as `2.0-notification-service`. **CSS, SVG, fonts and images stay file-based**, exactly as they are now.

Scope:

- Only the student gradesheet goes in the database. **`id-card` stays file-based** — that's the current situation and it stays that way; it is not seeded, and the classpath fallback is what keeps it working, not a temporary stand-in for a later migration. The split is deliberate: with one report on each path, file-based and database-based templating can be exercised and tested independently, using the same code, instead of both reports always taking the same route.
- The table stores the HTML and the key used to find it. None of notification-service's other columns (module, feature, subject, layout, variables, audit fields and so on) are needed.
- No admin API. Rows are loaded and edited with SQL.

**The request does not change.** Existing clients send the same curl:

```
curl --location 'http://localhost:8081/api/v1.0/print' \
  --form 'report="admission/id-card.html"' \
  --form 'template="id-card"' \
  --form 'file_name="id-card"' \
  --form 'data="{...}"'
```

Paths below that are written as `service/...`, `entity/...` and so on are under `src/main/java/com/bracits/easyJavaPdf/`.

## 1. How a report request works today

`HtmlToPdfController` → `PdfService` picks the strategy with the lowest priority number whose `supports()` returns true. When `report` is set that is `ReportBasedGenerationStrategy` (priority 10).

1. It creates a temp directory for the request.
2. [`ReportTemplateService.prepareTemplate`](src/main/java/com/bracits/easyJavaPdf/service/ReportTemplateService.java#L51) does three things:
   - Normalizes `admission/id-card.html` to `admission/id-card`.
   - Finds `classpath:/reports/admission/id-card.html` and copies the raw file to `<tmp>/admission/id-card.html`.
   - Because `template=id-card`, copies everything in `classpath:/templates/id-card/` into `<tmp>/admission/`, next to the HTML, with no subfolders.
3. The strategy reads the raw HTML back ([line 106](src/main/java/com/bracits/easyJavaPdf/service/strategy/ReportBasedGenerationStrategy.java#L106)). It renders it with Thymeleaf as an inline string, using `data` (or `data_set`) as the model, and writes the result over the same file.
4. The first `.css` file that was copied becomes `cssFile`. The renderer's base URI is `htmlFile.getParent()` ([`ITextPdfGenerator:146`](src/main/java/com/bracits/easyJavaPdf/service/ITextPdfGenerator.java#L146)). That is how `logo.svg`, `brandBandUg.svg`, `./style.css` and the fonts are found as local relative files.

**What this means for the design:** the rendered HTML still has to be written to disk next to the assets. The database only changes where the markup string comes from. The temp directory, the asset copying and the renderers stay as they are.

## 2. How notification-service loads templates from the database

| Piece | What it does |
|---|---|
| `NotificationTemplate` entity, `NotificationTemplateRepository.findByKey` | A row has a unique `key` and a `body` that holds Thymeleaf markup. |
| `NotificationTemplateResolver extends StringTemplateResolver` | Handles only template names that match `@html/*` (and the other `@` prefixes). It loads the row by key and passes the **body** to `super.computeTemplateResource(...)`, so the body becomes the template. It returns `null` when no row exists. |
| Registration | The resolver is a plain `@Component`. Spring Boot's `ThymeleafAutoConfiguration` adds every `ITemplateResolver` bean to the `SpringTemplateEngine` automatically. |
| Call site | `templateEngine.process("@html/" + key, context)`. |
| Caching | Thymeleaf caches the parsed template. `UpdateTimeCacheEntryValidity` treats the cache entry as valid while a flag exists in a Spring Cache. The JPA `@PreUpdate` listener (`AuditableEntityListener`) clears that flag when the entity is saved through JPA. |

Checked against Thymeleaf 3.1.5, the version java-pdf resolves: `StringTemplateResolver` has `setCacheTTLMs(Long)`. When `computeTemplateResource` returns `null`, `AbstractTemplateResolver.resolveTemplate` returns `null` and the engine tries the next resolver.

## 3. Design

### 3.1 Table: three columns

```sql
-- schema/pgsql.sql
create table pdf_report_templates (
    id   bigint generated by default as identity primary key,
    key  varchar(255) not null unique,
    body text not null
);
```

**The key is the normalized `report` value** the client sends, with any leading `/` and the `.html` suffix removed — but it is a lookup identifier, not a mirror of the classpath path, so it doesn't have to repeat the file's directory structure. For `student-grade`, that means the client now sends `report="student-grade.html"` (not the file's full `exam-controller/gradesheet/student-grade.html` path) for the request to hit this database row. `template="student-gradesheet"` is unaffected — the asset folder is resolved independently of the report key.

| key | body taken from | assets (still on the classpath) |
|---|---|---|
| `student-grade` | `src/main/resources/reports/exam-controller/gradesheet/student-grade.html` | `templates/student-gradesheet/` |

`admission/id-card` has **no row** — it is not seeded, so it always falls through to the classpath branch below, exactly as it does today. It can be added the same way later if that ever becomes the goal, but nothing here assumes it will be.

```sql
-- schema/seed-reports.sql   ($html$ quoting means the HTML needs no escaping)
insert into pdf_report_templates (key, body) values
  ('student-grade', $html$<!doctype html>...$html$)
on conflict (key) do update set body = excluded.body;
```

Neither HTML file contains the string `$html$`, so the quoting is safe.

### 3.2 New components

**`entity/ReportTemplate`**: `@Entity @Table(name = "pdf_report_templates")` with fields `id` (identity), `key` (unique) and `body` (`@Column(columnDefinition = "text")`, so that `ddl-auto=validate` passes).

**`repository/ReportTemplateRepository`**:

```java
public interface ReportTemplateRepository extends JpaRepository<ReportTemplate, Long> {
    Optional<ReportTemplate> findByKey(String key);
    boolean existsByKey(String key);
}
```

**`service/ReportTemplateResolver`**: the same pattern as `NotificationTemplateResolver`.

```java
@Component
@ConditionalOnProperty(name = "pdf.report.db.enabled", havingValue = "true")
public class ReportTemplateResolver extends StringTemplateResolver {

    private static final String PREFIX = "@report/";
    private final ReportTemplateRepository repository;

    public ReportTemplateResolver(ReportTemplateRepository repository,
                                  @Value("${pdf.report.db.cache-ttl:PT5M}") Duration cacheTtl) {
        this.repository = repository;
        setName("dbReportTemplateResolver");
        setResolvablePatterns(Set.of(PREFIX + "*"));
        setOrder(1);
        setCacheable(true);
        setCacheTTLMs(cacheTtl.toMillis());
        setCheckExistence(false);
    }

    public static String getPath(String key) {
        return PREFIX + key;
    }

    @Override
    protected ITemplateResource computeTemplateResource(IEngineConfiguration configuration,
                                                        String ownerTemplate,
                                                        String templateName,
                                                        Map<String, Object> attributes) {
        String key = templateName.substring(PREFIX.length());
        ReportTemplate template = repository.findByKey(key)
                .orElseThrow(() -> new ValidationException(
                        "Report template '" + key + "' not found in database"));
        return super.computeTemplateResource(configuration, ownerTemplate, template.getBody(), attributes);
    }
}
```

This does not override `computeValidity`. When a TTL is set, `StringTemplateResolver` already returns a `TTLCacheEntryValidity`.

### 3.3 Changes to existing classes

**[`service/ReportTemplateService`](src/main/java/com/bracits/easyJavaPdf/service/ReportTemplateService.java#L51)** takes an `ObjectProvider<ReportTemplateRepository>`. `getIfAvailable()` returns `null` when the database is off. `prepareTemplate` becomes:

```java
String key = normalizeReportName(reportName);
ReportTemplateRepository repository = repositoryProvider.getIfAvailable();

Path htmlTarget;
String dbTemplateName = null;
if (repository != null && repository.existsByKey(key)) {
    htmlTarget = workingDirectory.resolve(key + ".html");   // same layout as the classpath branch
    createParentDirectories(htmlTarget);
    dbTemplateName = ReportTemplateResolver.getPath(key);
} else {
    TemplateResource templateResource = locateTemplate(reportName);   // unchanged
    htmlTarget = workingDirectory.resolve(templateResource.relativePath());
    createParentDirectories(htmlTarget);
    copyResourceTo(templateResource.resource(), htmlTarget);
}
// copyAssetTree(...) and copyTemplateAssetsFlat(template, htmlTarget.getParent()) are unchanged for both branches
```

**`service/ReportTemplateDescriptor`** gets a new field, `String dbTemplateName`, which is `null` when the HTML comes from the classpath. A 4-argument constructor is kept so the existing `new ReportTemplateDescriptor(...)` calls in `ReportBasedGenerationStrategyTest` still compile.

**[`service/strategy/ReportBasedGenerationStrategy:106-107`](src/main/java/com/bracits/easyJavaPdf/service/strategy/ReportBasedGenerationStrategy.java#L106-L107)** gets one branch:

```java
String renderedHtml = descriptor.dbTemplateName() != null
        ? rendering.renderNamedTemplate(descriptor.dbTemplateName(), models)   // already exists, handles data_set
        : rendering.renderTemplate(Files.readString(descriptor.htmlFile(), StandardCharsets.UTF_8), models);
Files.writeString(descriptor.htmlFile(), renderedHtml, StandardCharsets.UTF_8);
```

**[`service/TemplateRenderingService:263-264`](src/main/java/com/bracits/easyJavaPdf/service/TemplateRenderingService.java#L263-L264)** needs a required fix; see risk A. Change the check from `resolver instanceof StringTemplateResolver` to `resolver.getClass() == StringTemplateResolver.class`.

### 3.4 Request flow after the change

The same `prepareTemplate` code handles both branches; which one runs depends only on whether the key has a row. The two shipped reports exercise one branch each, on purpose (see Context):

```
report=student-grade.html, template=student-gradesheet      <- DB branch
 └─ key = student-grade
    └─ in DB → <tmp>/student-grade.html ← engine.process("@report/student-grade")
                                            └─ ReportTemplateResolver → findByKey (cached, TTL)
 └─ copy templates/student-gradesheet/* flat into <tmp>/   (file-based, unchanged)
 └─ renderer, base URI <tmp>/                                (unchanged)

report=admission/id-card.html, template=id-card              <- classpath branch
 └─ key = admission/id-card
    └─ not in DB → classpath:/reports/admission/id-card.html → inline render (today's path)
 └─ copy templates/id-card/* flat into <tmp>/admission/    (file-based, unchanged)
 └─ renderer, base URI <tmp>/admission/                      (unchanged)
```

### 3.5 Configuration: the database is opt-in

Adding `spring-boot-starter-data-jpa` makes a DataSource required at startup. That would break the README's `docker run sanzar686/easyjavapdf` when no database is available. So the feature is turned on with a Spring profile.

`application.properties`:

```properties
pdf.report.db.enabled=false
pdf.report.db.cache-ttl=${PDF_REPORT_DB_CACHE_TTL:PT5M}
spring.autoconfigure.exclude=org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration,\
  org.springframework.boot.autoconfigure.orm.jpa.HibernateJpaAutoConfiguration
```

`application-db.properties` (new):

```properties
spring.autoconfigure.exclude=
pdf.report.db.enabled=true
spring.datasource.url=${DB_URL:jdbc:postgresql://localhost:5432/pdf_service}
spring.datasource.username=${DB_USER:admin}
spring.datasource.password=${DB_PASSWORD:admin}
spring.datasource.hikari.maximum-pool-size=${DB_POOL_SIZE:4}
spring.jpa.hibernate.ddl-auto=validate
spring.jpa.open-in-view=false
```

To enable it, set `SPRING_PROFILES_ACTIVE=db` (plus `DB_URL`, `DB_USER` and `DB_PASSWORD`). When `JpaRepositoriesAutoConfiguration` finds no DataSource, it backs off. The repository bean then doesn't exist, the resolver isn't created, and `ReportTemplateService` uses the classpath as it does today.

The default pool size of 4 matches `pdf.executor.max-size`. At most that many requests look up a key at the same time.

## 4. Where this differs from notification-service

| notification-service | java-pdf | Why |
|---|---|---|
| Cache is cleared by the JPA `@PreUpdate` listener through `TemplateCacheService` | Thymeleaf's built-in TTL expiry (`pdf.report.db.cache-ttl`) | java-pdf has no admin API, so templates are edited with SQL. SQL updates never fire a JPA listener, so copying that mechanism would serve the old HTML until restart. With the TTL, an edit shows up within 5 minutes. |
| module, feature, type, subject, layout, plainBody, variables, ref, enable, confidential, audit columns, Envers, `@Version` | `id`, `key`, `body` | Out of scope. |
| `LayoutTemplateResolver` and the layout dialect | None | Reports are complete HTML documents. |
| Key generated from the name on insert | Key is the report path | The curl already sends it. |
| Resolver returns `null` when the row is missing | Resolver throws `ValidationException` | See risk B. |

## 5. Decisions (proposed, waiting for confirmation)

1. **Look in the database first, then the classpath.** When the database has the key, its version wins, so an SQL edit takes effect without a redeploy. Reports with no row — `id-card`, `welcome-letter` — keep working from files, indefinitely, not just until a migration catches up. *Alternative:* database only, with no classpath branch at all — rejected because the stated goal is to keep both paths alive side by side for testing.
2. **The database is opt-in through the `db` profile** (section 3.5). *Alternative:* always require a database.
3. **Cache with a 5-minute TTL.** *Alternatives:* no cache (read the database on every render), or copy notification-service's clear-on-save mechanism, which is only useful if an admin API that writes through JPA is added later.
4. **PostgreSQL**, to match notification-service's `schema/pgsql.sql`.

## 7. Risks

**Risk A (high; would break every inline render if missed): the inline resolver would stop being registered.** `TemplateRenderingService.registerInlineTemplateResolverIfNecessary` registers its catch-all `StringTemplateResolver` only when the engine has **no** resolver for which `instanceof StringTemplateResolver` is true. `ReportTemplateResolver` is a subclass and is already on the engine when that constructor runs, because Boot adds resolver beans while it builds the engine. So the inline resolver would never be registered, and three kinds of request would break: `html` uploads, `htmlContent`, and classpath report rendering. Fix: `resolver.getClass() == StringTemplateResolver.class`. This needs a test.

**Risk B (medium): returning `null` would render the template name as text.** The inline resolver has no name pattern, so it accepts any template name as literal markup. If `ReportTemplateResolver` returned `null`, for example because the row was deleted between `existsByKey` and `findByKey`, the engine would fall through to the inline resolver. The PDF would then contain the literal text `@report/student-grade`. The resolver throws instead.

**Risk C (medium): an edit made during the TTL window.** A body updated with SQL appears after at most `pdf.report.db.cache-ttl`. That delay is the intended trade-off. Set it to `PT0S`, or turn caching off, when testing template edits.

**Risk D (low): one extra query per report request.** `existsByKey` hits a unique index. It is small next to a Chromium render that takes hundreds of milliseconds or more. If the database is unreachable, the request fails. It does not quietly fall back to what may be an out-of-date classpath file.

**Risk E (low): the word `key`.** It is not reserved in PostgreSQL, and notification-service already uses it as both a column and an entity field with `findByKey`. It is reserved in MySQL. If the service ever moves to MySQL, rename the column (for example `@Column(name = "report_key")`).

**Risk F (low): the seed content and the orphaned classpath file drifting apart.** `reports/exam-controller/gradesheet/student-grade.html` still exists on disk, but once the `student-grade` key is in the database it is never read again — the database always wins for that key. An edit made to the classpath file instead of the database row would silently do nothing. Worth a comment on the file itself, or deleting it, once the database path is confirmed working. This does not apply to `id-card` — it has no database row to be shadowed by, so its classpath file is still the live, single source of truth.

## 8. Tests

- **`ReportTemplateResolverTest`:**
  - `@report/student-grade` is turned into the key `student-grade`.
  - The body is returned when the row exists.
  - A `ValidationException` is thrown when it doesn't.
  - Names that don't start with `@report/` are not handled.
  - The TTL is applied.
- **`ReportTemplateServiceTest`:**
  - Key in the database (`student-grade`): no classpath lookup, the HTML path is `<wd>/student-grade.html`, the files from `templates/student-gradesheet/` sit next to it, and `dbTemplateName` is `@report/student-grade`.
  - Key not in the database (`admission/id-card`): today's classpath behaviour, with `dbTemplateName == null` — this is the regression test proving the file-based path is untouched.
  - No repository bean (database off entirely): both reports use the classpath behaviour.
- **`ReportBasedGenerationStrategyTest`:**
  - A database descriptor calls `renderNamedTemplate`.
  - A classpath descriptor still calls `renderTemplate(String, List)`.
- **`TemplateRenderingServiceTest`:**
  - When a `ReportTemplateResolver` is on the engine, the inline `StringTemplateResolver` is still registered.
  - Inline rendering still works. This is the regression test for risk A.

## 9. Verification

The database (container `pdf-service-db`, Postgres 16-alpine, `localhost:5432`, db `pdf_service`) is already created and seeded — `schema/pgsql.sql` and `schema/seed-reports.sql` have been applied, and `pdf_report_templates` has one row, `key = 'student-grade'`. Steps 1–2 below are what to do on a fresh machine; skip them here.

Because `id-card` and `student-grade` sit on opposite branches, they double as each other's control group — a regression in the database wiring should only ever move the `student-grade` result, never the `id-card` one, and vice versa.

1. Create the database, then run `schema/pgsql.sql` and `schema/seed-reports.sql`.
2. Start with `SPRING_PROFILES_ACTIVE=db ./run.sh`.
3. **File-based path.** Send the ID card curl from the Context section unchanged (`report="admission/id-card.html"`). Expect exactly the same output as before this feature existed: 2 pages per student, `Content-Disposition: attachment; filename=id-card.pdf`. This exercises the classpath branch and should be completely insensitive to whether the database is up, seeded, or has ever been touched.
4. **Database-based path.** Send the gradesheet request with the new key (`report="student-grade.html"`, `template="student-gradesheet"`, same `data`/`data_set` shape as before) and compare it with a PDF generated from the classpath file before the migration — they should match.
5. Change some visible text in the `student-grade` row with SQL (in DataGrip or `psql`). Re-run within the TTL: the old text still appears (proves caching works). Re-run after the TTL: the new text appears (proves the cache actually expires).
6. Delete the `student-grade` row and re-run: the request now fails validation-style (`ValidationException`, see risk B) rather than silently falling back — that's the intended behavior once a key is expected to be database-backed.
7. Restart without the `db` profile and with no database running at all. With the profile off, `ReportTemplateRepository` never becomes a bean, `getIfAvailable()` returns `null`, and `ReportTemplateService` never consults the database for either report. The app starts, and **both** `id-card` and `student-grade` render from their classpath files — `student-grade`'s only because `reports/exam-controller/gradesheet/student-grade.html` is still physically present (risk F); deleting it would break this specific case while the `db` profile is off, which is exactly why risk F flags it as worth a decision rather than deleting it right away.
